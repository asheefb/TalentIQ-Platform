* Spring Boot layered architecture:

  * Config (Optional) : Custom configurations for beans/security/etc.
  * Controller : Handles HTTP requests and responses.
  * Service : Contains business logic.
  * ServiceImpl (Optional) : Implementation class of the service interface.
  * Repository : Handles database operations using JPA.
  * Entity : Represents a table in the database.
  * DTO : Used for API input/output.
  * Exception (Optional) : Custom exceptions and handlers.

1. Entity :
        A Java Class mapped to a database table.
   * @Entity: Annotation that tells JPA/Hibernate to map this class to a database table.
   * @Id: Marks the primary key field of that table.
   * Spring Data JPA: Automatically generates SQL queries for basic CRUD operations (save, find, delete, update).
   * You don’t need to write SQL manually; JPA + Hibernate handles it internally.

2. DTO : A separate class used to receive or send data in APIs.
    * Why we use DTO instead of Entity:
      * Protects Entity from being exposed publicly
      * Keeps Api input clean
      * Allows Structure changes without breaking Api
      * Helps Add Validation later
      * Separates Api layer from database layer

3. Controller
   * Entry point of API
   * Handles HTTP methods (GET, POST, PUT, etc.)
   * Converts incoming JSON to DTO
   * Passes data to Service

4. Service
    * Contains business logic
    * Processes and validates data
    * Calls Repository for DB operations
    * Usually created as an interface (ex: UserService if we are maintaining impl)
    * Keeps Controller clean by separating logic
    * @Service annotation marks it as a service class

5. ServiceImpl (Optional)
    * Implementation of the Service interface
    * Contains actual logic of methods declared in Service
    * Uses Repository to save or fetch data
    * Some projects skip interface + implementation to reduce files
    * But having both increases clarity and testability
    * @Service annotation used here too

   Controller -> Service Flow
   1. Controller receives HTTP request
   2. Controller passes data (DTO) to Service
   3. Service has business logic
   4. Service calls Repository
   5. Repository saves/fetches data from DB
      * Controller = entry gate
      * Service = worker
      * Repository = storage
6. Repository
    * Handles database operations
    * Extends JpaRepository or CrudRepository
    * No need to write SQL for basic CRUD
    * Spring Data JPA auto-generates queries
    * Can create custom query methods like:
        * findByEmail
        * findByUsername
    * @Repository annotation (optional but good practice)
    * Repository = direct communication to database
7. Config (Optional)
    * Contains custom configurations
    * Used when default behavior is not enough
    * Examples:
      * Bean creation 
      * CORS configuration 
      * Security configuration 
      * Swagger config
    * @Configuration annotation used
    * Not required for basic CRUD projects

8. Exception (Optional)
    * Handles errors in one place instead of writing try-catch everywhere
    * Gives clean, understandable error messages
    * Useful for validation errors or custom errors
    * Example: UserNotFoundException
    * Uses:
      * @RestControllerAdvice 
      * @ExceptionHandler
    * Helps maintain clean and consistent error responses

This architecture helps keep large applications maintainable and modular.
